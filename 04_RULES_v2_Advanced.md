# LocalBench --- Engineering Rules v2.0

**Status:** v2.0 (Advanced)\
**Revision Date:** August 2026\
**Audience:** Development team, code review, decisions

---

## Core Philosophy

LocalBench is an **offline-first, measurement-driven engineering project.** Every major decision should optimize for:

1. **Privacy** — No external dependencies, no telemetry.
2. **Reproducibility** — Same input → same output.
3. **Reliability** — Fail loud, recover safe.
4. **Transparency** — Show methodology, raw data, limitations.
5. **Simplicity** — Avoid unnecessary abstraction and dependencies.

**Decision Framework:** When in doubt, choose the option that makes results more measurable and explainable.

---

## 1. Offline-First Principle

**Rule:** The normal execution path must NOT require cloud LLMs or external AI APIs.

**What This Means:**
- All inference happens locally via Ollama.
- No fallback to cloud APIs (fail locally instead).
- No required cloud authentication.
- No external model leaderboards required (benchmark locally).

**What You CAN Do:**
- Reference public leaderboards in documentation (for context).
- Provide optional integration hooks for future cloud adapters (but don't implement).
- Document how to extend with custom runtimes.

**What You CANNOT Do:**
- Add a fallback to GPT API if Ollama is slow.
- Use cloud embedding services for document retrieval.
- Send benchmark results anywhere without explicit user action.
- Require internet connection for normal CLI operation.

**Enforcement:**
- Code review: Does this call an external API? If yes, question why.
- Testing: Run full benchmark suite offline (Ollama on localhost).
- Documentation: "Inference: LOCAL" must appear in README.

## 2. Measurement Before Claims

**Rule:** Never claim one model is "best" without specifying context.

**What This Means:**
- Every recommendation must include:
  - Workload (what task?).
  - Hardware (what constraints?).
  - Benchmark version.
  - Dataset version.
  - Metrics (what's measured?).
  - Constraints applied (what filtered out other models?).

**What You MUST Include in Reports:**
- Sample size (how many test cases?).
- Evaluation methodology (how is quality scored?).
- Measurement methodology (how are latency/RAM measured?).
- Limitations (why might results differ on another machine?).
- Model versions (exact Ollama pull command).
- Timestamp (when was this run?).

**What You CANNOT Say:**
- "Model X is universally best."
- "Model X is always fastest."
- "Quality score of 92% = production ready."

**Enforcement:**
- README template: "Results are specific to..."
- Every benchmark report: methodology section mandatory.
- Every recommendation: explanation mandatory.
- Code review: Challenge any superlatives.

---

## 3. Raw Data First Principle

**Rule:** Never discard raw benchmark outputs. Aggregate metrics are derived, not source of truth.

**What This Means:**
- Every benchmark run persists:
  - Raw text generated by model.
  - Raw timing measurements.
  - Raw resource samples.
  - Raw evaluation details.
- Summary metrics and scores are calculated FROM raw data.
- Never delete raw outputs to "clean up" reports.

**Artifact Structure:**
```
results/<run-id>/
├── metadata.json           # What was run
├── config.json             # How it was run
├── system.json             # Hardware context
├── raw_outputs.jsonl       # Every model output (immutable)
├── case_results.jsonl      # Parsed results (immutable)
├── summary.json            # Aggregated metrics
└── report.md               # Human-readable report
```

**Enforcement:**
- All `.jsonl` files are immutable (never rewritten).
- Summary is regenerated from raw data (not the reverse).
- Code review: Question any metric not traceable to raw data.

## 4. Reproducibility Requirement

**Rule:** Every benchmark result must record enough metadata to reproduce identically.

**What This Means:**
- Metadata must include:
  - Software version (git commit hash).
  - Benchmark version.
  - Dataset version.
  - Model identifiers (exact `ollama pull` command or Ollama model hash).
  - Generation configuration (temperature, max_tokens, etc.).
  - Hardware profile (CPU, RAM, Ollama version).
  - Timestamp.

**Reproduction Test:**
- Same machine, same config → identical results (bit-for-bit same latency is impossible, but within 5% is okay).
- Different machine, documented differences → results scale predictably.

**Enforcement:**
- Every `BenchmarkRun` includes full metadata.
- README includes "reproducibility" section.
- Test: Run same benchmark twice, compare results (accept ±5% noise on metrics).

## 5. Model Abstraction Rule

**Rule:** Application code must NOT directly depend on Ollama-specific details.

**What This Means:**
- Only `localbench.runtime.ollama_adapter` knows about Ollama HTTP API.
- Everyone else uses `LocalModel` protocol.
- Model interaction goes through abstraction.

**Code Pattern (GOOD):**
```python
def run_benchmark(model: LocalModel, cases: list[BenchmarkCase]):
    for case in cases:
        result = model.generate(request)  # Generic LocalModel
```

**Code Pattern (BAD):**
```python
def run_benchmark(ollama_client, model_name: str):
    response = ollama_client.generate(prompt=...)  # Ollama-specific
```

**Enforcement:**
- Code review: Is Ollama referenced outside `runtime` module? If yes, refactor.
- Tests: Mock `LocalModel` protocol, not Ollama HTTP.

## 6. Schema + Validation Rule

**Rule:** Anything crossing a component boundary should have a typed contract. Validate at boundaries.

**What This Means:**
- Pydantic models for all data structures.
- Strict mode: `ConfigDict(validate_assignment=True)`.
- Serialization/deserialization is tested.
- Invalid data is rejected early, not silently coerced.

**Code Pattern (GOOD):**
```python
class GenerationRequest(BaseModel):
    model_config = ConfigDict(validate_assignment=True)
    prompt: str
    temperature: float = Field(0.0, ge=0.0, le=2.0)
    max_tokens: int = Field(512, gt=0, le=4096)
```

**Code Pattern (BAD):**
```python
def generate(prompt, temperature=None, max_tokens=None):
    if temperature is None: temperature = 0.0
    # No validation of range
```

**Enforcement:**
- Code review: New data class? Make it a Pydantic model.
- Tests: Roundtrip serialization (Python → JSON → Python).

## 7. Structured Output Validation Rule

**Rule:** Never trust model-generated structured output. Always parse and validate.

**What This Means:**
- JSON extraction → Pydantic validation → only then use.
- Validation failures are classified (recoverable vs. not).
- Retries happen for recoverable failures.
- Non-recoverable failures are clear errors.

**Code Pattern (GOOD):**
```python
raw_output = model.generate(prompt_for_json_output)
try:
    parsed = Quiz.model_validate_json(raw_output)
    return parsed
except ValidationError as e:
    # Classify, maybe retry, or raise
```

**Code Pattern (BAD):**
```python
output = model.generate(prompt_for_json_output)
json_data = json.loads(output)  # Could crash
quiz = Quiz(**json_data)  # No validation
```

**Enforcement:**
- All structured generation goes through `StructuredGenerator`.
- Tests: Malformed JSON, missing fields, wrong types all tested.

---

## 8. Retry Policy Rule

**Rule:** Retries must be bounded, observable, reason-based, and limited to recoverable failures.

**What This Means:**
- `max_attempts` is hard limit (default: 3).
- Every attempt is logged with:
  - Attempt number.
  - Raw output.
  - Error category.
  - Duration.
  - Validation details.
- Retries only on recoverable failures (schema validation, JSON parse).
- Non-retryable: timeout, model unavailable, configuration error.

**Retry Categories:**

| Error | Recoverable? | Rationale |
|-------|--------------|-----------|
| JSON parse error | Yes | Model might recover with corrected prompt |
| Schema validation error | Yes | Could be close; feedback might help |
| Timeout | No | If model is hung, retrying won't help |
| Model unavailable | No | Infrastructure problem |
| Invalid config | No | User error; don't retry |
| Empty output | No | Model broken; don't retry |

**Code Pattern (GOOD):**
```python
result = StructuredGenerationResult(
    attempts=3,
    valid=True,
    parsed=parsed_object,
    attempt_log=[
        AttemptRecord(attempt_number=1, ...),
        AttemptRecord(attempt_number=2, ...),
        AttemptRecord(attempt_number=3, ...),
    ]
)
```

**Enforcement:**
- Tests: Malformed JSON on attempt 1 → retry attempt 2 with diagnostics.
- Tests: Max attempts exhausted → clear error.
- Code review: Unbounded retry? Reject.

## 9. Error Handling Rule

**Rule:** Do not silently swallow exceptions. Classify, log, and handle explicitly.

**What This Means:**
- Define typed exceptions for each error category.
- Catch only specific exceptions (not broad `Exception`).
- Log context, not just the error.
- Return typed results where possible.
- Propagate only when appropriate.

**Exception Hierarchy:**

```python
class LocalBenchError(Exception):
    code: str
    message: str
    context: dict

class RuntimeUnavailable(LocalBenchError):
    code = "RUNTIME_UNAVAILABLE"

class ModelNotFound(LocalBenchError):
    code = "MODEL_NOT_FOUND"

class ValidationError(LocalBenchError):
    code = "VALIDATION_ERROR"

class BenchmarkError(LocalBenchError):
    code = "BENCHMARK_ERROR"
```

**Handling by Layer:**

| Layer | Strategy |
|-------|----------|
| Runtime adapter | Raise typed exceptions. Don't catch. |
| Generation | Classify, retry if appropriate, else raise. |
| Benchmark | Catch, log, record in result, continue run. |
| CLI | Catch, format message, exit with code. |

**Enforcement:**
- Code review: Bare `except` clauses? Question why.
- Tests: Every typed exception has a test.

## 10. Logging and Privacy Rule

**Rule:** Do not log full user documents or sensitive prompts by default.

**What This Means:**
- Logs contain operational information (model name, timing, error category).
- Logs do NOT contain:
  - Full user prompts or questions.
  - Document content.
  - Sensitive benchmark results (before user approves sharing).
  - Personal information.

**What You CAN Log:**
- Model name and version.
- Latency and throughput.
- Error category and code.
- Resource usage (peak RSS, CPU%).
- Configuration parameters (excluding secrets).

**What You CANNOT Log:**
- User question text (log category, not question).
- Benchmark case answers (log evaluation result, not text).
- Document file contents.
- API keys or credentials.

**Enforcement:**
- Code review: `log.info(prompt)` in generation? Reject; log category instead.
- Privacy audit (Phase 10): Search logs for user data. Should find none.

## 11. Benchmark Fairness Rule

**Rule:** When comparing models, use identical conditions.

**Fair Comparison Requires:**
- Same dataset version.
- Same prompts (word-for-word).
- Same generation parameters (temperature, max_tokens).
- Same hardware (or documented differences).
- Same model versions.
- Same evaluation rules.
- Consistent warm-up.
- Separated cold/warm measurements (if relevant).

**What You CANNOT Do:**
- Compare Model A with temperature=0.7 vs. Model B with temperature=1.0.
- Compare Model A on GPU vs. Model B on CPU (without labeling).
- Compare two different dataset versions and claim one model is "better."
- Mix cold-start and warm latencies in comparison.

**Enforcement:**
- `BenchmarkConfig` locks all parameters.
- Every `CaseResult` records full generation config.
- Report includes "Configuration" section.

## 12. Evaluation Methodology Rule

**Rule:** Prefer deterministic evaluation. If using LLM-as-judge, label clearly.

**Evaluation Strategies (Ranked by Preference):**

| Rank | Strategy | When to Use | Limitations |
|------|----------|-------------|-------------|
| 1 | Exact match | Factual answers (capitals, dates) | Doesn't handle paraphrasing |
| 2 | Keyword coverage | Conceptual answers (must mention key terms) | Doesn't check quality of explanation |
| 3 | Numeric tolerance | Math/calculation problems | Only works for numeric output |
| 4 | Structured field validation | JSON/table generation | Checks format, not semantics |
| 5 | LLM-as-judge | Open-ended answers | Introduces judge bias; label clearly |

**If Using LLM-as-Judge:**
- Record which judge model and version.
- Document judge limitations in report.
- Label metrics as "judge-scored" (not "ground truth").
- Do NOT claim judge score is objective.
- Test: Does judge score correlate with human review? (on 3–5 samples)

**Enforcement:**
- Code review: LLM judge in evaluation? Must have metadata and limitations doc.
- Report includes "Evaluation Methodology" section with clarity.

## 13. Recommendation Explainability Rule

**Rule:** Recommendations must be explainable. Show why selected and why rejected.

**Recommendation Must Include:**
- Recommended model name.
- Why selected (what constraints passed? what score?).
- Hard constraints applied (min quality, max RAM, etc.).
- Rejected models with violation reasons.

**Code Pattern (GOOD):**
```
RECOMMENDATION

Qwen (7B)

Why selected:
  ✓ Quality 87% >= 85% (threshold)
  ✓ RAM 6.2 GB <= 8 GB (threshold)
  ✓ Latency 1.2s <= 3s (threshold)
  → Highest quality among qualifying models

Rejected:
  Mistral 7B: Quality 72% < 85% (below minimum)
  Llama 13B: RAM 10.4 GB > 8 GB (exceeds budget)
```

**Code Pattern (BAD):**
```
Recommendation: Qwen

Score: 0.89

[No explanation]
```

**Enforcement:**
- Tests: Recommendation includes explanation.
- Code review: No "black box" recommendations.

## 14. Dependency Rule

**Rule:** Do not introduce a dependency unless it solves a concrete problem in the current phase.

**What This Means:**
- Prefer stdlib when possible (json, pathlib, typing).
- Add a dependency only if:
  - Required for core functionality (e.g., Pydantic for validation).
  - Significantly reduces code (e.g., Rich for terminal output).
  - Mature and well-maintained.
- Document the reason for each dependency in `pyproject.toml`.

**Explicitly DO NOT Use (Yet):**
- LangChain (not needed for this project scope).
- Vector databases (keyword search is sufficient).
- FastAPI (no web service needed).
- Async/await frameworks (benchmark is sequential).
- Cloud SDKs (offline requirement).

**Enforcement:**
- Code review: New import? Justify in PR.
- Pyproject comments: Why does each dependency exist?

## 15. Scope Rule

**Rule:** Build the smallest robust version first. Don't add features preemptively.

**What's IN Scope (P0):**
- Benchmark engine (20–30 cases).
- Model evaluation and comparison.
- Constraint-based recommendation.
- Study assistant (Q&A, basic quiz).

**What's OUT of Scope (P1+):**
- Web UI.
- Vector semantic search.
- Multi-GPU distribution.
- Agents or multi-step tasks.
- Flashcards or spaced repetition.
- A/B testing framework.

**Why:**
- Scope creep kills execution.
- P0 is credible as a portfolio project.
- P1 can follow naturally if P0 is solid.

**Enforcement:**
- PRDs and tech spec lock scope explicitly.
- Code review: Is this P0 or P1? If P1, defer.

## 16. Testing Rule

**Rule:** Core components have tests. Failure paths are first-class test cases.

**Testing Tiers:**

| Tier | Coverage | Examples |
|------|----------|----------|
| Unit | 80%+ | Schemas, evaluators, metric calculators |
| Integration | Critical paths | End-to-end: models → benchmark → recommend |
| Failure | All major error paths | Ollama down, malformed JSON, timeout |

**Failure Tests (Non-Negotiable):**
- Ollama unavailable → clear error message.
- Model not found → suggest available models.
- Malformed JSON → retry with diagnostics.
- Schema validation failure → clear error.
- Timeout → don't retry, fail with context.
- No models qualify recommendation → explain why.
- Empty model output → error, not silent failure.

**Enforcement:**
- Code review: New component without tests? Request tests.
- Bug fix: Add regression test before fixing.
- Merge: CI must pass (tests + linting).

## 17. Naming Rule

**Rule:** Use explicit, descriptive names. Avoid vague names.

**Good Names:**
- `BenchmarkRunner` (does what it says).
- `StructuredOutputValidator` (clear responsibility).
- `RecommendationEngine` (clear purpose).
- `ResourceProfiler` (clear domain).
- `evaluate_keyword_match()` (specific function).

**Avoid:**
- `Manager` (too generic).
- `Helper` (vague).
- `Utils` (catch-all; don't use).
- `Processor` (unclear what it processes).
- `process()` (ambiguous verb).
- `data` (what data?).
- `result` (what result?).

**Enforcement:**
- Code review: Vague names? Request rename.

## 18. Documentation Rule

**Rule:** Architecture changes require documentation updates. Methodology changes require version updates.

**When to Document:**
- New module: Add docstring explaining responsibility.
- New public class/function: Add docstring with examples.
- Architecture change: Update tech spec.
- Evaluation methodology change: Increment benchmark version.
- Dataset change: Increment dataset version.
- Bug fix affecting results: Update changelog.

**Enforcement:**
- PR review: Doc changes included? If no, ask why.
- Release: Changelog updated? If no, can't release.

## 19. Git / Version Control Rule

**Rule:** Use small, focused commits. Clear commit messages. Clean history.

**Commit Message Format:**

```
feat(module): description

Longer explanation if needed.

Closes #123 (if applicable)
```

**Types:**
- `feat` — new feature.
- `fix` — bug fix.
- `test` — test changes.
- `docs` — documentation.
- `refactor` — code reorganization (no logic change).
- `chore` — dependencies, build, etc.

**Examples:**
```
feat(runtime): add OllamaModel adapter
feat(benchmark): implement keyword evaluation strategy
fix(generation): handle empty model output
test(recommendation): add constraint filtering tests
docs(benchmark): document evaluation methodology
```

**Enforcement:**
- Code review: Unclear commit message? Rewrite.
- History: Should be readable without `git log --all`.

## 20. Security Rule

**Rule:** Never commit secrets, keys, or sensitive data.

**Must NOT Commit:**
- API keys or tokens.
- Personal documents or data.
- Credentials or passwords.
- Machine-specific paths or IPs.
- Benchmark results with sensitive content.
- Private/confidential benchmark outputs.

**Must Use:**
- `.gitignore` for local files.
- `.env` files (not committed).
- Environment variables for secrets (if needed).

**Enforcement:**
- Pre-commit hook: Prevent accidental commits.
- Code review: Check for secrets.
- Before release: Audit repo for leaks.

## 21. Performance Rule

**Rule:** Do not optimize based on intuition. Profile, optimize, measure.

**What This Means:**
- Before optimizing, identify bottleneck (profiling).
- Optimize only the bottleneck.
- Measure impact (is it faster? by how much?).
- Accept if improvement is <5% (overhead not worth it).

**Acceptable Optimizations:**
- Caching model instances (not reloading per case).
- Batch resource sampling (not per-millisecond).
- Connection pooling to Ollama.

**Avoid:**
- Premature parallelization (benchmark is sequential by design).
- Micro-optimizations (import order, variable naming).
- Complex data structures for marginal gains.

## 22. Architecture Layering Rule

**Rule:** Keep responsibilities separated. Data flows predictably through layers.

**Data Flow:**
```
User Input (CLI)
    ↓
Application Logic (Workload, Benchmark)
    ↓
Generation (Validation, Retry)
    ↓
Runtime (Model Abstraction)
    ↓
Ollama Adapter
    ↓
Ollama (local)
```

**What Each Layer MUST NOT Do:**
- CLI: Business logic (only routing).
- Application: Direct Ollama calls (use runtime abstraction).
- Benchmark: Direct structured generation (use generation layer).
- Runtime: Retry logic (that's generation's job).

**Enforcement:**
- Code review: Does layer A depend on layer C (skipping B)? Reject.

## 23. Design for Trust Rule

**Rule:** Communicate trustworthiness through clarity, not decoration.

**What to Show:**
- Raw metrics.
- Methodology.
- Constraints applied.
- Failures (not hidden).
- Limitations.
- Model versions.

**What to Avoid:**
- Colored badges or "awards."
- Subjective superlatives ("best," "optimal").
- Hidden aggregate scores.
- Unexplained recommendations.

**Code Pattern (GOOD):**
```markdown
## Benchmark Results

| Model | Quality | Latency | RAM |
| ... | ... | ... | ... |

### Methodology
Evaluation: keyword coverage. 20 OS questions. Qwen 7B-Q4.

### Limitations
Small sample size (20 cases). Results specific to this machine (8GB RAM).
```

**Code Pattern (BAD):**
```markdown
## Results

⭐⭐⭐⭐⭐ Qwen is BEST

Quality: 87/100
```

## 24. Portfolio Rule (Critical)

**Rule:** This project is for portfolio review. Every decision should demonstrate engineering discipline.

**Reviewers Will Assess:**
- Architecture clarity and modularity.
- Rigor of evaluation methodology.
- Testing and error handling.
- Honesty about limitations.
- Reproducibility of results.
- Code quality and documentation.

**What Impresses Reviewers:**
- ✓ Sound benchmark methodology.
- ✓ Comprehensive error handling.
- ✓ Clear contract definitions (Pydantic).
- ✓ Reproducible results.
- ✓ Honest about limitations and trade-offs.
- ✓ Clean, readable code with tests.

**What Turns Off Reviewers:**
- ✗ Unrealistic claims ("Model X is universally best").
- ✗ Weak evaluation (biased dataset, poor methodology).
- ✗ No tests or error handling.
- ✗ Buried limitations or unreproducible results.
- ✗ Scope creep (half-finished features).
- ✗ Black-box scoring with no explanation.

**Enforcement:**
- Ask: "Would a senior engineer be impressed by this design?"
- If no, reconsider approach.

## 25. Definition of Engineering Quality

**Rule:** A feature is not complete when it works once.

**Completeness Checklist:**

- [ ] **Clear ownership:** Who is responsible? (Code ownership, comment or doc).
- [ ] **Defined contract:** What are inputs/outputs? (Pydantic schema or docstring).
- [ ] **Error handling:** What happens if input is invalid? What if process fails?
- [ ] **Tests:** Does it pass tests for happy path and failure cases?
- [ ] **Documentation:** Can someone else understand this from docstrings + inline comments?
- [ ] **Observable behavior:** Can you see what it's doing (logs, metrics)?
- [ ] **Reproducible:** Same input → same output (every time)?

**Enforcement:**
- Code review: Does this meet all 7 criteria? If not, request improvements.
